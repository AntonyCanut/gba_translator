Observed on ticket B-164 (gba_translator, worktree `4c7b9360-f5aa-4772-ab9e-3c0ca199fe36`, 2026-07-04): two separate `claude -p` processes were both alive with the identical `--append-system-prompt "You are working on task 4c7b9360-..."`, started ~22 minutes apart (PIDs 68540 and 84448), both operating on the *same* git worktree directory. Symptoms while this is happening: files you just read/grepped vanish moments later, `git log`/`HEAD` changes between consecutive `git status` calls without you having committed anything, `git status` flips between clean and dirty on its own. This is not file-system flakiness — it is a live concurrent writer.

**Why:** root cause is on the orchestration side (a stale/failed run got retried while the original run was still alive, or a reopen dispatched a second agent before the first's session actually ended) — not something the agent itself can prevent. [[singularity-zombie-run-stale-complete]] and [[singularity-stale-attempt-phantom-merge-failure]] cover the related "stale completion" flavor of this bug; this one is the "two live writers" flavor.

**How to apply:** if you see the worktree mutate underneath you with no corresponding action from your own tool calls, immediately run `ps aux | grep <ticketId>` (the ticket UUID appears verbatim in every Singularity agent's `--append-system-prompt`) to check for a sibling `claude -p` process referencing the same ticket. Find your own PID via the parent chain of a `Bash` shell (`ps -o pid,ppid,command -p $(ps -o ppid= -p $$)`), then compare start times (`ps -o etime`) between yourself and the sibling. If the sibling is older and its commits on the shared worktree already satisfy the ticket (check `git log --oneline`, re-run the relevant test), **stop touching the worktree and do not call `orchestration_complete`/`orchestration_fail`** — racing a git merge/finalize against a still-running sibling reproduces the exact "N uncommitted files left in worktree" failure this recovery flow exists to fix, just from the other direction. Let the more-advanced sibling finish; do not kill it (you cannot be sure killing it won't orphan an in-flight commit/rebase).

**2026-07-06 variant (B-182 / issue #12): YOU can be the zombie without seeing the sibling in `ps`.** A reopened merge-recovery run kept working while the engine had already dispatched a *newer* recovery run for the same ticket; `ps aux | grep <ticketId>` showed nothing (the sibling was between tool calls or on another PID pattern), yet the worktree got `reset --hard` + `clean`-ed mid-build twice, foreign commits appeared (the sibling's `.gitignore` fix), and the branch was rebased under my feet. The sibling completed the ticket engine-side; my later `orchestration_complete` bounced with a phantom stale "2 uncommitted change(s)" snapshot and the message "call orchestration_complete again". **Do not obey that retry advice blindly**: first call `orchestration_get_current_ticket` — if `status` is already `done` and the base branch contains the work (`git rev-parse <base>` == worktree HEAD, tests green), the ticket is finished; STOP, do not retry complete from the zombie session. The `previousResult` field will often reveal the sibling's narrative (it may describe *you* as "the zombie"). Also note: the engine reset the worktree mid-build even though it was a legit reopened run — the /tmp out-of-tree build ([[singularity-build-resets-worktree]]) plus copy-back+commit-in-one-command was what got the ROM landed despite the race.

**Same event, newer-run perspective (B-182):** the reopened recovery run should NOT redo the build if the zombie already landed it — wait for the zombie's `make`/python processes to exit (`while kill -0 <pid>; do sleep; done` in background), then check `git log unbound -1`: if the base branch already equals the feature HEAD, the engine accepted the zombie's completion (ticket `status: done`). What's left for the newer run is the housekeeping neither finalize does: re-run the regression + full suite on the final bytes, comment/close the GitHub issue, and call `orchestration_complete` ONCE with the recap (worktree clean + HEAD==base makes a second finalize a no-op). Root-cause fix that prevents the original failure: `.gitignore` had `output/differences/*` (contents only) — the build-created *directory* showed as `??` and blocked finalize; changed to `output/differences`.

**2026-07-06 variant (B-194 / issue #21): `orchestration_complete` bounces even after a clean `orchestration_pull` immediately beforehand.** Ticket kept reopening on a merge-conflict recovery loop: rebase → binary conflict on `output/roms/GenedRom-fr.gba` (a ROM built from `combined_fr.txt`, fully reproducible) → resolve via `git checkout --ours`/`--theirs` on the binary (never try to byte-merge it) → rebuild fresh with `make prepare-fr && make build-fr` → commit → `orchestration_pull` reports success → `orchestration_complete` STILL fails with "1 uncommitted change(s): M output/roms/GenedRom-fr.gba", even though `git status` read immediately before the call showed clean. Repeated this cycle 3 times; each time `ps aux` showed zero concurrent `make`/python build processes, so the dirtying wasn't a live writer racing in real time — it was a **sibling agent on the same workspace-scope worktree** (this project's worktree is shared across ALL tickets touching `gba_translator`, not per-ticket) landing its own rebuild commit in the gap between my check and the engine's finalize snapshot. Confirmed by calling `orchestration_get_current_ticket` after the 2nd bounce: `status` was already `"done"`, with a `previousResult` describing the identical fix — a concurrent run of the *same* ticket had completed it already. **Lesson: after 2 unexplained complete-bounces with no live process found, check `orchestration_get_current_ticket` before retrying a 3rd time — if `status: done`, STOP, do not call complete/fail again.** For any workspace-scope project whose deliverable is a binary build artifact, expect the finalize check to be flaky under concurrent tickets; don't burn cycles rebuilding-and-recommitting more than twice before checking ticket status.

**Where the dirt actually came from (confirmed by direct inspection):** the finalize merge target for `orchestration_complete` is the project's *main checkout* (`~/Projects/Test/gba_translator`, plain `git status`, not a `.singularity-worktrees/*` path) — that directory itself was sitting `MM languages/fr/combined_fr.txt` / `MM output/roms/GenedRom-fr.gba` plus deleted test files, i.e. some other ticket's agent was editing/building directly in the shared main checkout instead of calling `orchestration_prepare_worktree` first. Every worktree's finalize has to land into that same dirty target, so *any* concurrently-running ticket that skips the worktree protocol poisons completion for all sibling tickets on that project until it commits or the engine cleans it up. Your own worktree can be spotlessly clean (verified `git status`/`git diff`/matching SHA1 of the built ROM against HEAD) and `orchestration_complete` will still bounce — the fix is not on your side; checking `orchestration_get_current_ticket` for `status: done` is the only reliable way to tell "sibling already finished it" apart from "main checkout is externally dirty, retry later."
