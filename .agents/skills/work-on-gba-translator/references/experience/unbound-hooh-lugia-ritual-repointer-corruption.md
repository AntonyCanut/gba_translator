B-56 « Oh oh » **RÉSOLU — c'EST une régression de la build FR** (les 7 passes précédentes qui ont conclu « pas une régression » avaient TORT). Trouvé en faisant enfin le repro dynamique in-engine que les passes précédentes déclaraient « impossible ».

**mGBA tourne en headless ici** — la croyance « mGBA n'avance pas les frames sans focus » est FAUSSE : `EmulatorBridge.start(rom, headless=True)` connecte, avance les frames, lit la mémoire, screenshot. Tout le cul-de-sac de 7 passes vient d'avoir hérité cette hypothèse sans la tester. **Leçon capitale : ne jamais hériter d'un « can't repro » — dépenser un appel d'outil pour vérifier que le harness échoue vraiment avant de basculer sur une méthode plus faible.**

**Preuve dynamique** : même save batterie (`GenedRom sauvegarde.sav`, salle « Ruines du Néant B2F », tile 14,22) + même difficulté → la ROM **anglaise** lance le combat Ho-Oh automatiquement après la cutscene de summon ; la build **FR** se fige sur « Hoo hoo hoo ! » avec Ho-Oh debout dans l'overworld, le combat ne démarre jamais (et Lugia n'arrive jamais). L'utilisateur avait raison. (Repro : descendre vers la sortie sud pour ré-armer la cutscene, masher A ; surveiller `gBattleTypeFlags` 0x02022B4C → bascule à 0x42000 quand le combat démarre.)

**Cause racine** : `gba_translator/scripts/repoint_stale_text_pointers.py` réécrit les « pointeurs stale » en scannant CHAQUE fenêtre de 4 octets égale à l'ancienne adresse GBA d'une chaîne relocalisée. Dans le script du rituel la suite `setflag 0x08E2; setflag 0x09F6` se lit little-endian `0x09F62908` — l'adresse anglaise de la chaîne SANS RAPPORT « I swam, of course! ». La passe a faux-positivé et écrasé ces octets de script avec l'adresse française relocalisée `0x08C277E1` (« J'ai nagé, bien sûr ! »), cassant la chaîne setflag → la cutscene n'atteint plus `setwildbattle` + `special 0x138`. Même corruption 2×: **0x1E8C677 (branche Ho-Oh)**, **0x1E8C782 (branche Lugia)**. Le seul veto de la passe était pour les octets de *texte traduit*, PAS le *bytecode de script*.

**Pourquoi le test byte-analysis MASQUAIT le bug** : l'ancien `test_only_pointer_relocations_differ` classait tout diff ≤4 octets comme « relocalisation de pointeur » dès que l'ancien ET le nouveau mot ressemblent à des pointeurs ROM. La fenêtre corrompue fait exactement ça (0x09F62908 → 0x08C277E1) → test VERT sur la ROM cassée. **Leçon capitale : un classifieur générique « ça ressemble à un pointeur » ne peut PAS distinguer un vrai pointeur relocalisé d'un bytecode de script qui égale par hasard une adresse de chaîne. Épingler les octets de script précis contre la source anglaise.**

**Fix** : `gba_translator/scripts/patch_legendary_ritual_fr.py` restaure les octets canoniques (`08 29 F6 09`) aux 2 sites depuis la ROM anglaise (lancé en dernier dans `build-fr`, après `repoint_stale`) ; + un veto `PROTECTED_SCRIPT_OFFSETS = {0x1E8C677, 0x1E8C782}` dans `repoint_stale_text_pointers.py` pour empêcher la re-corruption. Vérifié in-engine : le combat Ho-Oh se lance (`gBattleTypeFlags`→0x42000) et la cutscene va jusqu'au bout (joueur rendu au contrôle dans la salle vidée), dialogues FR (dont « Hoo hoo hoo ! ») préservés. ROM live déjà patchée.

**L40 vs L75 n'est PAS une branche difficulté** (la passe 9 avait tort aussi) : Ho-Oh/Lugia **level 40** (0x1E8C68E / 0x1E8C798) = la cutscene de SUMMON scriptée (celle que B-56 figeait) ; **level 75** (0x1E8CC34 / 0x1E8CB9B) = l'« anneau mystérieux » Hoopa autonome dans lequel on entre manuellement (« sauf si on va vers lui »).

**P-70 / Groudon (2026-06-22) — 3e instance du MÊME bug** : la cutscene d'invocation Groudon (« Groudon ! Réponds à mon Orbe Rouge ! ») bouclait sans lancer le combat. Site **0x1E59D1F** (script du rituel Orbe Rouge, distinct du cluster Ho-Oh/Lugia 0x1E8Bxxx), MÊME signature exacte : EN `08 29 F6 09` (`setflag 0x08E2`/`setflag 0x09F6`) → FR `E1 77 C2 08` = MÊME pointeur corrompu `0x08C277E1`, juste avant son propre `setwildbattle`+`special 0x138` (0x1E59D74 = `25 38 01`). Un SCAN ROM-WIDE du pointeur corrompu `0x08C277E1` a révélé que le bug touche **13 sites** au total, pas 3 : Ho-Oh/Lugia/Groudon + **10 autres scripts de cutscene** (0x1E5DB34, 0x1E5EE6F, 0x1E5F2F2, 0x1E78496, 0x1E7A6F4, 0x1E7A7ED, 0x1E99463, 0x1EAD4BE, 0x1EAE183, 0x1EAE83B), chacun = la queue d'une chaîne `setflag X; setflag 0x09F6`. 2 sites (0x1E8738D, 0x1E873B4) ont les MÊMES octets mais sont de VRAIS pointeurs texte relocalisés (à GARDER en FR). **Classifieur fiable** : clobber-script ⟺ `EN==08 29 f6 09` ET `EN[off-2]==0x29` (opcode setflag avant la fenêtre) ; vrai pointeur ⟺ octet précédent ≠ 0x29.

**⚠️ RÉOUVERTURE P-70 (2026-06-22, commit 3d2737a) — la « fix racine » e032518/2a505ba N'A JAMAIS ÉTÉ committée dans le code.** Le résumé du run précédent (et l'ancienne version de cette mémoire) DÉCRIVAIT `discover_clobbered_sites()` + veto général `_is_setflag_chain` — mais le code réellement committé ne contenait QUE la liste codée en dur 2 sites (`RITUAL_SCRIPT_FIXES = {0x1E8C677, 0x1E8C782}` dans le patch ET `PROTECTED_SCRIPT_OFFSETS` = ces 2 seuls dans le repointer). Résultat : le rebuild ROM commit 8f7bc06 (« Leveinard cry ») a re-clobberé les 11 autres sites (dont Groudon 0x1E59D1F), le patch n'en a restauré que 2 → l'utilisateur a toujours bouclé sur Groudon. **LEÇON CAPITALE : un résumé de complétion n'est PAS une preuve que le code committé fait ce qu'il décrit — vérifier les OCTETS de la ROM trackée (`git cat-file -p HEAD:output/roms/GenedRom-fr.gba`) et lire le code source committé, pas le récit.** Diagnostic : `rom[0x1E59D1F:+4]` == `e1 77 c2 08` (clobber) sur la ROM trackée alors que Ho-Oh/Lugia == `08 29 f6 09` (sains) = preuve directe que seuls 2/13 sites étaient protégés.

Fix RACINE réellement committée en 3d2737a au lieu d'une liste d'offsets qui grossit : (1) repoint_stale → garde générale `_is_setflag_chain(rom,loc)` = `rom[loc-2]==0x29 and rom[loc+1]==0x29` qui veto TOUTE fenêtre setflag-chain pour n'importe quelle string relocalisée ; (2) patch_legendary_ritual_fr → `discover_clobbered_sites(source)` scanne EN pour chaque fenêtre `08 29 f6 09` précédée de 0x29, restaure les 11 clobbers, exclut les 2 vrais pointeurs (off-2≠0x29). PREUVE in-engine before/after cette fois (pas juste byte-exact) : re-break du SEUL site Groudon → la cutscene boucle (dialogue overworld Marlon/Véga cycle, Groudon jamais summon, pas de combat) ; ROM restaurée → Groudon apparaît + combat se lance (menu party in-combat « Choisis un Pokémon/Envoyer »). Harness `scripts/groudon_drive.mts` (warp via échelle map 0.0→1.52, mash A, classer). **PIÈGE détection : flags `inBattle`/`textActive`/`cb1` du bridge mGBA == TOUJOURS faux/0 sur cette build CFRU (cf [[unbound-mgba-harness-flags-invalid]]) — juger par SCREENSHOT, pas par flag.** Nouveau garde déterministe `test_no_legendary_setflag_chain_is_clobbered` (e2e, scanne les 13 sites de la ROM buildée, sans mGBA) — l'ancien test ne couvrait QUE la région Ho-Oh/Lugia 0x1E8Bxxx, d'où Groudon passait inaperçu. Suite rapide 575 verte.

**PIÈGE worktree Singularity (commit 2bb42b0)** : un ticket concurrent a REBUILD `output/roms/GenedRom-fr.gba` (tracké en git !) avec l'ANCIEN repoint → a RÉINTRODUIT les 11 clobbers (la ROM live patchée hors-worktree ne compte pas, c'est la ROM trackée du worktree qui est mergée). Après `orchestration_pull` qui signale la ROM dans les fichiers changés : re-lancer le patch sur la ROM du worktree + la committer. LEÇON : si le build FR vit dans un repo qui track la .gba, tout patch byte post-build doit être re-committé après un rebuild concurrent.
